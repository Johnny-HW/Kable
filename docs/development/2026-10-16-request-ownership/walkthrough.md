# 요청 소유권 및 동시 시작 취소 개발 완료

검증일: 2026-10-16. [승인된 개발 계획](implementation_plan.md)의 두 항목만 수정했다.

## 1. 동일 CID의 새 요청 보존

기존 finally의 `TryRemove(cid, out _)`는 이전 요청 A의 응답 디스패치 후
같은 CID로 등록된 B를 삭제할 수 있었다.

이제 ConcurrentDictionary의 `ICollection<KeyValuePair<...>>.Remove`를 사용해
키와 TCS 값이 모두 일치할 때만 원자적으로 제거한다.
TCS는 해당 요청의 인스턴스이므로 B로 교체된 항목은 A가 제거할 수 없다.
조회와 삭제를 분리하지 않았고 추가 래퍼·배열·문자열 할당은 도입하지 않았다.

`CidOwnershipTests`는 응답 추적 콜백에서 B를 등록하여 A의 finally 이전에
경쟁 구간을 만든다. 임의 sleep이나 스레드 스케줄 확률에 의존하지 않는다.
다음 세 시나리오를 확인했다.

- A가 정상 반환한 뒤 B의 응답도 정상 전달된다.
- A가 InvalidCastException으로 끝나도 B가 보존된다.
- 취소된 요청은 자기 항목을 정리하고 동일 CID의 후속 요청이 성공한다.

## 2. 동시 시작 호출의 개별 취소

후속 StartAsync는 기존 취소 대기 도우미로 공유 시작 작업을 기다린다.
호출별 linked token을 사용하며, 후속 호출 취소로 공유 연결 작업을 취소하지 않는다.
기존 최초 호출자의 연결 수명과 실패 처리, ConnectAsync 단일 호출은 유지한다.

`ConcurrentStartCancellationTests`는 연결 팩토리 완료를 gate로 제어한다.

- 연결 진행 중 대기자 하나를 취소하면 그 대기는 연결 완료 전에 취소된다.
  최초 시작·다른 대기자·연결 토큰은 유지되고 gate 해제 후 연결된다.
- 이미 취소된 후속 호출도 공유 연결에 영향을 주지 않는다.
- 연결 실패는 취소하지 않은 대기자들에게 동일 예외로 전달된다.

## TDD와 검증

- 유효한 재현 테스트 6건을 기존 코드에 실행: 3건 실패 / 3건 통과.
  CID 경쟁 2건과 시작 대기 취소 1건이 실패했다.
- CID 수정 후 관련 회귀 테스트: 16개 통과.
- 시작 취소 수정 후 관련 수명 테스트: 12개 통과.
- `dotnet build src/Kable/Kable.csproj --no-restore --verbosity quiet`:
  netstandard2.0, net8.0, net10.0 빌드 성공, 경고 0 / 오류 0.
- `dotnet build Kable.sln --no-restore --verbosity quiet`:
  성공, 경고 0 / 오류 0.
- `dotnet test Kable.sln --no-build --no-restore -m:1 --verbosity quiet`:
  12개 프로젝트, 총 366개 통과 / 실패 0 / 건너뜀 0.
  핵심 프로젝트 294개, 기타 프로젝트 72개다.
- `git diff --check` 통과. 변경 코드 파일은 85~295줄로 모두 300줄 미만이다.

최초 테스트 작성 중 Task의 구체 런타임 타입을 잘못 검증한 assertion을
할당 가능 타입 검사로 바로잡은 뒤 실제 타임아웃 결함을 재현했다.
인덱스는 HEAD로 복원하고 작업 파일을 보존하여 검증 단계를 다시 실행했다.

## 범위와 한계

공개 API와 FIFO/CID 연결 수명 계약은 유지했다. 기존 테스트의 assertion이나
timeout을 완화하지 않았다. 앞선 작업에서 관찰한 부하 민감성을 고려해 최종 검증은
프로젝트 순차 실행을 사용했다. 기본 병렬 실행의 반복 안정성을 새로 검증하지 않았다.

CID 소유권 수정은 이전 요청의 정리가 새 요청을 삭제하는 문제를 해결한다.
장비가 타임아웃된 과거 요청의 응답을 같은 CID로 늦게 보내는 경우의 세대 구분은
프로토콜 정책에 관한 별도 문제이며 이번 수정에 포함하지 않았다.
실제 장비 시험과 신규 성능 벤치마크는 수행하지 않았다.
