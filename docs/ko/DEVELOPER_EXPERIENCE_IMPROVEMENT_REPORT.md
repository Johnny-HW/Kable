# Kable 개발자 사용성 개선 보고서

## 적용 상태 (2026-10-01 갱신)

시작 가이드·QuickStart·분류 옵션에 이어, 기본 요청 제한시간 전달과 동일 타입 요청 확장 메서드, Simple의 설정 모델 연결, 빌더의 세션·하트비트 옵션, 선택적인 자동 재연결 래퍼를 적용했다. 기존 종료한 세션을 재사용하지 않고 새 클라이언트를 생성하며 명령을 자동 재전송하지 않는다.

이벤트 계약 테스트, 실제 TCP 단절 복구 테스트, 코덱 인코딩 테스트를 추가했다. 문자열 송신의 임시 배열을 제거하고 코덱·세션 벤치마크 16개를 Release에서 실행했다. 측정 결과와 한계는 [성능 기준](PERFORMANCE_BASELINE.md), 사용법은 [API 가이드](DEVELOPER_USAGE.md)에 기록했다.

Release 전체 테스트 299개와 QuickStart 실행이 통과했다. 최초 사용자 3명의 사용성 실험, 실장비 검증, Linux CI 원격 실행 및 모든 타깃의 성능 측정은 수행하지 않았다. 별도의 UI 자동 전달 어댑터는 추가하지 않고 Dispatcher 사용 예제와 이벤트 계약을 제공했다.

아래 본문은 개선 방향 수립 시의 문제·제안·완료 기준을 보존한 것이다. 현재 구현 상태는 위 갱신 내용과 API 가이드를 참고한다.

작성일: 2026-10-01  
대상: 현재 작업 공간의 Kable 소스, 공개 API, README 및 테스트  
목적: 개발자가 문서만으로 연결·질의·이벤트 처리·장애 복구를 구현할 수 있도록 개선 방향과 실행 기준을 제시한다.

## 1. 평가와 개선 목표

Kable은 간단한 장비 연결을 빠르게 시작할 수 있는 좋은 기반을 갖고 있다. `KableSimple`의 연결과 질의 API, 전송과 코덱의 분리, 시뮬레이터, 주기적 폴링 프로필은 장비 개발자의 반복 작업을 줄인다.

현재 가장 큰 개선 과제는 기능의 수보다 동작의 예측 가능성이다. 기본 응답 분류, 타임아웃과 취소 이후의 세션 상태, 설정값의 적용 범위가 사용자의 직관과 다를 수 있다. 문서 예제에도 구현과 맞지 않는 부분이 있다.

권장 목표는 다음과 같다. 아래 수치는 달성된 결과가 아닌 제안하는 완료 기준이다.

| 목표 | 완료 기준 |
| --- | --- |
| 처음 연결하기 | 처음 사용하는 C# 개발자 3명이 로컬 모의 장비 예제를 각각 15분 이내 실행 |
| 문서 신뢰성 | 실행형 C# 예제를 샘플 프로젝트로 관리하고 CI에서 모두 빌드 |
| 설정 신뢰성 | 공개 설정마다 적용 대상·기본값·검증 규칙을 설명하고 동작 검증 |
| 응답 분류 | `!OK`, `#123`, 일반 응답과 자발 이벤트를 장비 규칙에 맞게 구분 |
| 장애 복구 | 타임아웃·취소·단절별 예외, 세션 상태, 복구 방법을 한 표로 제공 |
| UI 통합 | 이벤트 호출 스레드와 UI 전환 방법을 실행 가능한 예제로 제공 |

## 2. 평가 근거와 한계

앞선 평가에서 `KableSimpleTests` 4개를 실행했으며 모두 통과했다. 이번 보고서 작성에서는 관련 코덱, 세션, 프로필, 설정, DI 코드와 기존 테스트를 추가 확인했다. 전체 솔루션 테스트, 실장비, 패키지 배포 여부, 성능 벤치마크는 검증하지 않았다.

주요 근거 파일은 다음과 같다. 경로는 저장소 루트 기준이다.

- `src/Kable/Codecs/AsciiLineCodec.cs`
- `src/Kable/Engine/KableSession.Messaging.cs`, `KableSession.Loops.cs`, `KableSession.Lifecycle.cs`

## 3. 개선 과제와 우선순위

### 3.1 P0 — 복사해서 실행할 수 있는 시작 가이드

**문제:** README의 리플레이 예제는 현재 세션 API에 없는 `ProcessPacketAsync`를 호출한다. 테스트 가이드는 작업 공간에 없는 `Kable.slnx` 경로를 사용한다. 설치부터 실행까지 이어지는 최소 경로도 보강해야 한다.

**개선:** README 첫 부분을 준비 조건 → 참조 추가 → 로컬 모의 장비 실행 → 실제 연결 전환 순서로 구성한다. 배포된 NuGet 패키지와 버전을 확인하기 전에는 설치 가능성을 단정하지 않고 프로젝트 참조 경로를 제공한다. 실제 빌드 대상인 샘플을 문서 예제의 원본으로 사용한다.

리플레이는 현재 API가 제공하는 입력 경로로 작성하고, 세션에 직접 주입할 수 없는 경우 그 한계를 명시한다. 문서 편의를 위해 새로운 공개 메서드를 급히 추가하지 않는다.

**대상:** `README.md`, `README.ko.md`, `tests/README.md`, 신규 `samples/Kable.QuickStart/`.

**완료 기준:** 새 작업 환경에서 가이드대로 실행할 수 있고, 예제 빌드와 로컬 질의·응답 검증이 CI에서 통과한다. 장비 주소나 COM 포트가 필요한 예제는 별도로 표시한다.

### 3.2 P0 — 장비별 응답·이벤트 분류 설정

**문제:** 기본 문자열 코덱은 `$`, `#`, `!`, `*` 접두사를 자발 이벤트로 분류한다. 따라서 `!OK`와 같은 정상 응답이 질의를 완료하지 못할 수 있다. Simple API에는 이 규칙을 직접 바꾸는 옵션이 없다.

**개선:** 문자열 코덱에 선택적인 자발 이벤트 판별 함수를 제공하고 Simple API에서도 구성할 수 있게 한다. 기존 접두사 규칙은 호환성을 위해 유지하되 이름과 의미를 명시한다. 옵션을 늘릴 경우 전용 Simple 옵션 객체를 검토하고, 기존 호출 형태는 유지한다.

세션은 별도의 알람 판별도 수행하므로, 자발 이벤트 판별만 변경하면 모든 분류가 바뀐다고 설명해서는 안 된다. 알람의 우선 처리와 사용자 규칙의 관계도 명세한다.

**대상:** `AsciiLineCodec.cs`, `KableSimple.cs`, 신규 `Simple/KableSimpleOptions.cs`; 신규 `tests/Kable.Tests/Cases/Codecs/AsciiLineRoutingTests.cs`, `Cases/Simple/KableSimpleRoutingTests.cs`.

**검증:** 기존 기본 동작, 사용자 규칙에서의 `!OK` 응답, 응답 대기 중 자발 이벤트 도착, 일반 이벤트와 알람의 우선 처리, 분할 수신을 먼저 테스트한다.

**완료 기준:** 장비별 분류 규칙을 상위 API에서 지정할 수 있고, 이벤트가 진행 중인 요청의 응답으로 잘못 소비되지 않는다.

### 3.3 P0 — 타임아웃·취소·재연결 계약 명확화

**문제:** FIFO 요청에서 락 획득 후 처리 중 타임아웃이나 취소가 발생하면 세션이 종료된다. 락 대기 중 취소와는 동작이 다르다. 종료한 세션은 다시 시작할 수 없다. 이는 늦은 응답의 오매칭을 막는 설계이지만 사용자가 복구 흐름을 직접 알아내야 한다.

**개선:** 먼저 현재의 안전한 동작을 정확히 문서화한다. 요청 전 취소, FIFO 대기 중 취소, 요청 처리 중 취소, 응답 타임아웃, 물리 단절, 상관 ID 요청을 구분해 예외와 상태를 설명한다. 새 클라이언트 생성과 이벤트 재구독을 포함한 복구 예제를 제공한다.

자동 재연결은 후속 선택 과제로 분리한다. 구현 시 엔진의 단일 수명 계약을 유지하고 상위 계층에서 새 세션을 생성한다. 진행 중 명령은 실패로 종료하며 자동 재전송하지 않는다. 읽기 재시도와 이동·쓰기 명령 재시도는 별도 정책으로 다룬다.

**대상:** `IKableSimpleClient.cs`, `src/Kable.Core/IDeviceSession.cs`의 API 설명, 신규 `docs/ko/CONNECTION_LIFECYCLE.md`, 복구 샘플. 자동 복구 구현은 별도 승인 범위.

**검증:** 기존 `CancellationEdgeTests`, `WatchdogTimeoutAndDisconnectTests`를 검토하고, 늦은 응답이 새 요청에 매칭되지 않는지와 새 클라이언트의 연결·재구독을 검증한다.

**완료 기준:** 사용자가 예외를 받은 뒤 동일 객체를 재사용할 수 있는지와 다음 조치를 문서에서 판단할 수 있다.

### 3.4 P1 — 타임아웃 설정의 의미와 적용 통일

**문제:** `KableDeviceOptions.TimeoutMs`는 요청 기본 제한시간으로 설명되지만 빌더에서는 Named Pipe 연결 제한시간에 사용된다. TCP·시리얼 질의 기본 제한시간으로 전달되지 않는다.

**개선:** 연결 제한시간과 명령 응답 제한시간을 별도 설정으로 구분한다. 예를 들어 `ConnectTimeout`과 `DefaultRequestTimeout`을 제안한다. 두 이름은 확정 API가 아니다. 기존 `TimeoutMs`의 실제 적용을 유지하는 호환 경로와 새 속성의 우선순위를 명시한다.

기본 요청 제한시간은 요청 인자가 생략되는 상위 API에서 적용하고, 명시된 제한시간은 우선한다. 모든 전송에 연결 제한시간을 제공하려면 연결 팩토리의 취소 동작까지 확인한다. 값이 0 이하일 때 무제한인지 오류인지도 통일한다.

**대상:** `KableDeviceOptions.cs`, `KableClientBuilder.cs`, Simple 옵션·질의 코드, 필요 시 TCP·Named Pipe 연결 팩토리, `Cases/Configuration/` 테스트.

**완료 기준:** 연결 제한시간과 응답 제한시간을 독립적으로 검증할 수 있고, 문서상의 설정 효과가 실제 동작과 일치한다.

### 3.5 P1 — 이벤트 수신 범위와 UI 스레드 계약

**문제:** `LineReceived`는 백그라운드에서 호출된다. 요청 응답으로 소비된 메시지는 이 이벤트로 전달되지 않는다. 일반 이벤트 이름만 보면 모든 수신 라인이 전달된다고 오해할 수 있다.

**개선:** 기존 이벤트의 범위를 명시하고 WPF `Dispatcher` 전환 예제를 제공한다. 전체 패킷 확인은 옵저버와 터미널 경로를 안내한다. 느린 핸들러가 스트림 소비를 지연시킬 수 있다는 점도 설명한다.

새 이벤트나 자동 UI 전달 기능은 필요성이 확인된 후 추가한다. 제공한다면 WPF 의존성을 코어에 넣지 않고 UI 어댑터에서 처리하며, 큐 용량과 종료 시 처리를 명세한다.

**대상:** `IKableSimpleClient.cs`, `KableSimple.cs`, WPF 사용 가이드와 샘플, 신규 `Cases/Simple/KableSimpleEventContractTests.cs`.

**완료 기준:** 질의 응답과 자발 이벤트의 전달 범위가 검증되고, UI 예제가 안전하게 화면을 갱신한다.

### 3.6 P1 — 일반 빌더에서 고급 옵션까지 연결

**문제:** 세션에는 하트비트와 큐·알람 정책 옵션이 있지만 일반 빌더에는 이를 설정하는 경로가 없다. 기능이 필요해지는 순간 직접 세션 생성으로 전환해야 한다. `RequestAsync<TResponse>`도 실제 응답과 다른 타입을 지정하면 런타임 변환 오류가 날 수 있다.

**개선:** 빌더에 세션 옵션과 하트비트 구성 경로를 추가하는 방안을 검토한다. 처음 시작하는 가이드에는 필요한 설정만 보여주고 고급 페이지에서 나머지를 설명한다. 메시지 타입과 같은 응답을 반환하는 요청 편의 API는 기존 인터페이스 구현자에게 영향을 적게 주는 확장 메서드 방식부터 검토한다.

**대상:** `KableClientBuilder.cs`, 신규 `Extensions/KableSessionRequestExtensions.cs`, `Cases/Transports/` 빌더 테스트. 옵션과 코덱 책임은 기존 계층에 유지한다.

**완료 기준:** 간단한 사용에서 고급 구성으로 이동할 때 연결 코드 전체를 다시 작성할 필요가 없다.

### 3.7 P2 — 성능 주장과 측정 결과 정합성

**문제:** 문자열 송신은 `Encoding.GetBytes`로 배열을 생성하고 수신은 문자열을 생성한다. 따라서 전체 API를 무할당으로 이해하게 만드는 표현은 정확하지 않다.

**개선:** 파이프라인 버퍼 처리, 코덱, 문자열 API, 로깅을 구분해 성능 설명을 작성한다. Release 벤치마크로 메시지 크기·타깃 프레임워크·옵저버 유무별 할당량과 처리량을 측정한다. 측정 전에는 무할당 또는 극저할당 달성을 단정하지 않는다.

송신의 임시 배열 제거는 직접 버퍼 인코딩으로 검토할 수 있다. 수신 문자열 할당을 피하려면 별도의 바이트·구조체 API와 메모리 수명 계약이 필요하므로 후속 성능 과제로 분리한다.

**대상:** README 성능 설명, `AsciiLineCodec.cs`, `tests/Kable.Benchmarks/CodecBenchmarks.cs`, `SessionBenchmarks.cs`.

**완료 기준:** 공개 성능 주장을 재현할 수 있으며 문자열 API와 성능 중심 API의 비용 차이가 설명된다.

| 2 | 응답 분류 구성과 타임아웃 설정 정리 | 선행 테스트, 기존 호출 호환성, 장애 주입 검증 |
| 3 | 빌더 고급 옵션과 요청 편의 API | 공개 API 호환성 및 옵션 전달 검증 |
| 4 | 성능 측정과 문구 수정 | Release 벤치마크와 결과 기록 |
| 별도 | 자동 복구와 UI 전달 어댑터 | 재연결·명령 재전송·큐 정책 별도 설계 승인 |

이 보고서는 구현 승인 요청이나 코드 변경 완료 보고가 아니다. 실행 시 작업 공간 규칙에 따라 각 단계의 구체적인 변경 파일과 계획을 제시하고 승인을 받은 뒤 진행한다.

새 코드·테스트 파일은 각 300줄 미만을 목표로 하고, 기존 파일이 커지면 책임별 파일과 하위 폴더로 분리한다. Simple, Codecs, Configuration, Engine의 테스트는 대응하는 도메인 구조로 배치한다. 새 기능은 테스트를 먼저 작성하고 검증된 단위마다 마이크로 커밋한다.

기존 작업 변경을 보존하며, 실패 시 원인과 변경 범위를 확인한다. 작업 규칙에 따른 리셋도 사용자 변경을 제거하지 않는 범위로 한정한다.

## 5. 출시 전 검증 기준

- 지원하는 세 타깃의 라이브러리 빌드와 관련 단위·통합 테스트가 통과한다.
- 기존 Simple 호출과 기본 응답 분류를 유지하거나, 변경이 필요한 경우 마이그레이션을 명시한다.
- 응답 지연·분할 수신·단절·취소·늦은 응답을 장애 주입 테스트로 검증한다.
- 샘플은 고정 지연에 의존하기보다 준비 완료 신호와 제한시간을 사용한다.
- 문서 예제는 실제 공개 API로 컴파일되며 지원되지 않는 기능은 명시한다.
- 최초 사용자 검증에서 연결, 이벤트, 타임아웃 후 복구를 구현하는 데 막힌 지점을 기록한다.

## 6. 권고

첫 개선 범위는 시작 가이드와 API 계약 정리, 장비별 응답 분류, 타임아웃 설정 정합성으로 잡는 것이 좋다. 현재의 간단한 연결 경험을 유지하면서 개발자가 구현 내부를 읽어야 하는 상황을 줄일 수 있다.

자동 재연결은 편의성 효과가 크지만 장비 명령의 중복 실행과 수명 관리에 영향을 준다. 문서와 핵심 설정을 먼저 정리한 뒤 별도 설계로 진행하는 것을 권장한다.
