# C# 성능 개선 제안 재검토 보고서

검토일: 2026-10-27. 대상: 현재 작업 트리의 구현과 저장된 측정 자료.

## 1. 결론과 검토 범위

C#으로 개선할 후보는 있으나, 현재 자료만으로 개선 폭이나 실장비 체감 효과를 확정할 수 없다.
우선순위는 불필요한 복사 확인 → 대기 구조 검증 → 시나리오별 측정이다.
배치 도입, 버퍼 풀링, Rust 전환을 일괄적인 개선책으로 제안하지 않는다.

이 문서는 검토와 후속 실행 계획이다. 프로덕션 코드·테스트·공개 API는 변경하지 않았다.
사용자의 보고서 작성 요청을 문서 작성 승인 범위로 해석했다.
구현은 AGENTS.md의 Plan → Review → Execute 절차에 따라 별도 승인 후 진행한다.
기존 작업 트리에 있던 변경은 검토 시점 상태로 읽었으며 수정하거나 되돌리지 않았다.

## 2. 앞선 설명의 정정

1. “C#만으로 개선할 것이 많다”는 표현은 후보의 존재를 말할 수 있는 수준이었다.
   병목이나 개선량을 측정한 결과는 아니므로 큰 성능 향상을 의미하지 않는다.
2. 문자열 API의 수신 문자열 생성은 반환 타입에 따른 비용이다. 모두 불필요한 할당이 아니다.
3. 바이너리 `ToArray()`도 비동기 전달 시 데이터 수명을 보장한다. 단순 삭제 대상이 아니다.
4. 공유 메모리의 4KB 임시 배열은 수신 펌프 시작 시 한 번 생성된다.
   메시지마다 배열을 생성하는 문제와 구분해야 한다. 반복 비용은 그 배열을 거치는 추가 복사다.
5. 수신·디스패치 루프는 이미 도착한 데이터를 반복해서 처리한다.
   “메시지마다 반드시 대기한다”거나 “배치가 전혀 없다”는 해석은 잘못이다.
6. 앞서 인용한 88B·3.22KB는 예전 BenchmarkDotNet 산출물의 특정 조건 값이다.
   현재 전체 엔진의 할당이나 현재 구현의 대표값으로 사용하지 않는다.
7. 이벤트 대기의 50ms는 타임아웃 인자다. 신호가 오면 일찍 깨어날 수 있으므로
   이를 고정 50ms 수신 지연으로 해석하면 안 된다.

## 4. 우선 후보 상세

### A. 공유 메모리 수신의 추가 복사 제거

근거: `src/Kable.SharedMemory/SharedMemoryConnectionContext.cs:54`의 `PumpInboundAsync`.
현재 `SharedMemoryRingBuffer.Read(tempBuffer)`가 MMF에서 임시 배열로 복사한 뒤,
`CopyTo(mem.Span)`가 다시 Pipe 메모리로 복사한다.

제안: PipeWriter에서 확보한 메모리의 제한된 범위로 직접 `Read`하고 실제 읽은 만큼 Advance한다.
읽을 양은 기존 최대 4096바이트를 유지하는 안부터 검증한다.
이는 완전한 zero-copy가 아니라 MMF → Pipe 복사만 남기는 변경이다.
메시지를 모으는 추가 대기와 flush 정책 변경은 포함하지 않는다.

적합한 상황: 공유 메모리로 바이트 스트림을 지속 수신하는 경로.
한계: TCP·시리얼 및 파형 전용 API에는 직접 적용되지 않는다. 저속 장비에서는 효과가 작을 수 있다.
주의: 빈 읽기 이후 GetMemory 재사용, 취소, FlushAsync 포화, Complete 시 수명을 유지해야 한다.

검증: 1바이트·경계 크기·링 wrap-around·단편화·느린 소비자·취소·종료에서 바이트 동일성과 순서 검증.
비교: 64B/4KiB/64KiB 전송의 CPU/byte, 처리량, 단일 메시지 및 혼합 부하 p99 지연.
임시 배열 4KB 제거를 “메시지당 4KB 절약”으로 보고하지 않는다.

### B. 이벤트 대기 할당과 동기 대기

근거: `src/Kable.SharedMemory/Memory/SharedMemoryRingBuffer.cs:248` 이후.
WaitForData/WaitForSpace는 단일 이벤트를 `new WaitHandle[]`로 감싸 WaitAny를 호출한다.
취소 가능 시 매번 이벤트를 깨우는 callback도 등록한다.
연결 컨텍스트는 Task.Run으로 펌프를 시작하지만 내부의 이 대기는 동기식이다.

작은 변경 후보: 단일 핸들 대기에 맞게 배열 생성을 없애는 방법 비교.
이 변경만으로 비동기화나 ThreadPool 점유 문제가 해결되지는 않는다.
WaitOne으로의 치환도 취소, 타임아웃, Dispose, AutoResetEvent 신호 소비 의미를 확인한 뒤 결정한다.

구조 변경 후보: Windows 이벤트의 비동기 대기를 별도 어댑터로 캡슐화하는 설계.
프로세스 사이 신호이므로 프로세스 내부 SemaphoreSlim만으로 대체할 수 없다.
매 대기마다 등록·Task를 만드는 구현은 할당을 더 늘릴 수도 있으므로 재사용 여부를 비교한다.

적합한 상황: 유휴 또는 포화 상태로 대기하는 공유 메모리 연결이 많은 경우.
검증: 확인 직후 신호 도착, 등록 직전 취소, 대기 중 닫힘, 가짜/남은 신호, 포화 해소,
동시 Dispose에서 누락 깨우기·무한 대기·해제된 핸들 접근이 없어야 한다.
비교: 연결 1/32/128개에서 유휴 CPU, ThreadPool 스레드 수·큐 길이, 취소/종료 지연, 할당량.
기존 동기 대기를 Task.Run으로 한 번 더 감싸는 방식은 개선안으로 채택하지 않는다.

### C. 안전한 버퍼 수명 확보가 먼저 필요한 항목

근거: `src/Kable/Codecs/BinaryLengthPrefixedCodec.cs:36`의 ToArray와
`src/Kable/Engine/KableSession.Loops.cs:26`의 디코드 → dispatch queue → AdvanceTo 흐름.

현재 복사 결과는 Pipe가 소비 완료된 뒤에도 큐·요청 응답·스트림에서 읽을 수 있다.
단일 세그먼트라는 이유만으로 Pipe 메모리를 반환하면 AdvanceTo 이후 재사용에 노출된다.
ArrayPool 반환도 마지막 소비자가 누구인지 모르면 안전하지 않다.

판정: 기존 코덱의 복사는 유지한다. 대용량 바이너리에서 실제 병목이 확인된 경우에만
소유권을 명시한 별도 메시지/API를 설계하고 소비 종료·중도 취소·drop·오류의 반환 경로를 정의한다.
공개 IProtocolCodec 인터페이스 변경이나 기존 ReadOnlyMemory 반환 의미 변경은 승인 범위에서 제외한다.

### D. 문자열·알람 판별·관측

근거: `src/Kable/Codecs/AsciiLineCodec.cs:47`, `:91`.
현대 .NET 송신은 이미 출력 Span으로 직접 인코딩한다.
수신은 문자열을 생성하며, 여러 세그먼트에서는 풀 배열에 합친 뒤 디코딩한다.
TrimEnd는 입력에 따라 추가 문자열을 만들 수 있지만 항상 추가 할당하는 것은 아니다.

판정: string API를 유지한다. LF/CRLF·여러 세그먼트·ASCII/UTF-8·사용자 Encoding을 나눠
측정한 뒤 중복 변환이 확인된 조건만 최적화한다.
바이트에서 CR을 미리 제거하는 안은 임의 Encoding에서 의미가 같다고 가정할 수 없다.

알람 판별은 `KableSession.Loops.cs:122`와 `Streaming/KableSession.InboundBuffer.cs:32`에서
자율 메시지·알람 및 스트림으로 넘어가는 일부 메시지에 대해 반복될 수 있다.
DefaultIsAlarm의 일반 TMessage.ToString()은 타입에 따라 할당하거나 무거울 수 있다.
사용자가 제공한 IsAlarmMessage에는 상태나 부수효과가 있을 수 있어 호출 횟수 축소도 호환성 검토가 필요하다.

옵저버 호출은 `?.`로 보호된 곳이 있어, 옵저버가 없을 때도 해당 인자의 문자열 보간이
항상 실행된다고 단정하면 안 된다. 관측 off/on을 분리해 측정한다.
알람 분류 정확도와 요청 응답 매칭이 성능보다 우선한다.

## 5. 배치 처리의 시나리오별 판단

여기서 세 가지를 구분한다: 이미 도착한 데이터 배출, 개수/시간을 기다리는 축적,
최신 상태만 남기는 병합. 각각의 순서·지연·정보 보존 의미가 다르다.

| 시나리오 | 현재 근거와 판단 | 필요한 조건 |
| --- | --- | --- |
| FIFO 요청·응답 | 명령 축적 배치 제외 | 요청 순서·응답 매칭·송신 후 취소 시 세션 종료 계약 유지 |
| CID 다중 요청 | 이미 가능한 다중화와 배치는 별개 | 장비의 묶음 요청 지원 없이는 프로토콜 요청을 합치지 않음 |
| 긴급 송신·알람 | 배치 개수/시간을 기다리지 않음 | 기존 우선순위·오버플로 계약 보존. 물리적 즉시 실행의 보장은 아님 |
| 일반 수신·디스패치 | 이미 while TryDecode/TryRead로 도착한 메시지를 연속 처리 | 임의의 추가 축적 없이 현재 정책을 기준선으로 사용 |
| 고속 파형 | WriteBatch/ReadBatch가 이미 있음 | 장비가 자연스럽게 제공하는 블록 또는 허용 지연이 정해진 경우만 활용 |
| UI 상태 표시 | 최신값 병합 가능성 | 표시 중간값 생략 허용·표시 지연 상한·원본 기록과의 분리 |
| PCAP 기록 | 백그라운드 배출이 이미 있음 | 파일 반영 지연·오류·종료 시 drain 요구를 먼저 합의 |

파형 WriteBatch는 이미 샘플 여러 개 기록 후 Set을 한 번 호출한다.
TryWrite의 Set 호출이 많다는 이유만으로 빈→비어있지 않음 전이 때만 알리는 변경은 하지 않는다.
소비자 확인과 생산자 게시가 교차할 때 신호를 놓치지 않는 증명과 경합 테스트가 필요하다.
배치량과 추가 대기시간은 실사용 요구 없이 기본값을 임의로 제안하지 않는다.

UI 근거: `src/Kable.UI.Wpf/ViewModels/TelemetryStreamViewModel.cs:75`.
기존 항목은 수신마다 속성·시각 문자열을 갱신하고 신규 항목 등록만 Dispatcher를 사용한다.
UI 갱신 병합을 검토한다면 스레드 소유권과 Clear/Pause 경합도 함께 다뤄야 한다.
이 문서는 UI 스레드 오류의 재현이나 UI 성능 병목을 확정한 것은 아니다.

PCAP 근거: `src/Kable.Core/Observability/PcapWriter.cs`의 WriteCapturedPacketAsync.
레코드마다 헤더 배열과 BitConverter 임시 배열을 생성하고 FlushAsync를 호출한다.
헤더 할당 축소는 flush 정책과 별도로 검토할 수 있다. 비동기 쓰기 중 공유 헤더 재사용은
직렬화 구간 안에서만 안전하도록 설계해야 한다.
기록 payload 복사는 호출 뒤 원본이 바뀌는 것을 방지하므로 일괄 제거하지 않는다.
FlushAsync 완료를 저장장치 전원 장애까지 견디는 영속성 보장으로 해석하지 않는다.

## 6. 성능보다 먼저 확인할 공유 메모리 수명

파형 버퍼의 TryRead/TryWrite/배치/대기는 포인터 접근과 Dispose의 동시 실행 보호가 명확하지 않다.
RingBuffer에는 active I/O 카운터가 있지만 IsClosed의 사전 포인터 읽기와 대기 함수 등까지
해제 경합을 모두 보호하는지는 별도 감사가 필요하다.
이는 코드상 검토 우려이며 이번에 크래시를 재현한 결과가 아니다.
Rust 전환이나 풀링으로 해결됐다고 가정하지 않는다.

기존 SharedMemorySafetyTests에는 wrap-around·포화·동시 Dispose 테스트가 있다.
단시간 반복 스트레스 통과만으로 모든 interleaving이 안전하다고 결론 내릴 수 없다.
최적화 전 또는 같은 승인 단위의 선행 단계에서 제어된 경합 테스트를 마련한다.
생성·열기 실패 시 핸들/포인터 정리와 매핑 헤더 검증도 별도 수명 검토 항목이다.

## 7. 측정 자료 해석과 검증 계획

현재 성능 기준은 PERFORMANCE_BASELINE.md의 2026-10-01 자료를 우선 참고한다.
예: 32자 ASCII 송신 8.630ns/할당 미관측, 수신 45.738ns/120B.
32자 요청·응답(옵저버 없음)은 32.170µs/3662B이다.
이 수치는 현재 작업 트리를 새로 측정한 결과가 아니다.
측정은 .NET 10, 특정 PC, 짧은 반복에 한정되고 경고·넓은 신뢰구간이 있다.
인메모리 세션 할당에는 에코 서버·비동기 작업이 포함돼 엔진 단독 비용으로 해석하지 않는다.
Stream100은 OperationsPerInvoke=100의 메시지당 환산값으로 단일 메시지 지연과 다르다.

새 측정은 변경 전/후 동일 조건에서 수행한다. 프로토콜별 실제 프레임 크기·주기·버스트·장비 RTT는
아직 확보하지 못했으므로 아래는 검증용 입력이며 현장 대표값으로 주장하지 않는다.

- 요청·응답: 32/1024자, FIFO/CID, 관측 off/on, 무부하 및 텔레메트리 혼합.
- 공유 메모리: 단일 메시지·연속 스트림·간헐 버스트, 연결 1/32/128개, 느린 소비자.
- 파형: 단건 및 이미 준비된 블록, 별도의 축적 대기는 제외.
- 코덱: 단일/다중 세그먼트, LF/CRLF, ASCII/UTF-8, 비정상 프레임과 경계 크기.
- 기록/UI: 소비 지연·큐 포화·종료, 원본 순서/건수와 표시 생략 정책 검증.

평가 지표: 처리량, CPU/byte 또는 CPU/message, 할당/작업, GC 횟수·중단시간,
enqueue부터 실제 소비까지의 p50/p95/p99 지연, drop 건수, 큐 깊이, 취소·종료 시간.
현재 BenchmarkDotNet 평균만으로 p99나 GC 중단시간을 대신하지 않는다.
단일 측정의 작은 차이는 채택 근거로 쓰지 않고 여러 프로세스에서 재현성과 측정 변동을 비교한다.

채택 조건: 동일성·순서·수명·취소·포화 회귀 테스트 통과, 대상 비용 감소가 반복 측정에서 확인,
합의한 지연 상한과 자원 예산 준수. 상한은 실사용 시나리오 확인 후 확정하며 임의 숫자를 약속하지 않는다.
새 API·복잡성이 커지는 안은 현장 성능 이득이 그 비용을 정당화할 때만 승인 대상으로 올린다.

## 8. 승인 검토용 단계와 대상 파일

아래는 구현 확정 목록이 아닌 후속 승인 범위 제안이다. 새 파일은 각각 300줄 미만으로 구성한다.
기존 300줄 초과 RingBuffer 수정 시 대기·수명 책임을 분리하고 대응 테스트 폴더도 맞춘다.

1. 기준선과 공유 메모리 수명 검증부터 수행한다.
   - 신규 `tests/Kable.SharedMemory.Tests/Memory/RingBufferLifecycleTests.cs`
   - 신규 `tests/Kable.SharedMemory.Tests/Waveform/WaveformLifecycleTests.cs`
   - 수명 결함 재현 시 최적화와 분리한 수정 계획을 먼저 제시한다.
2. 수신 추가 복사 제거를 단독 구현·검증한다.
   - 수정 `src/Kable.SharedMemory/SharedMemoryConnectionContext.cs`
   - 신규 `tests/Kable.SharedMemory.Tests/Transports/InboundCopyTests.cs`
   - 신규 `tests/Kable.Benchmarks/SharedMemory/InboundCopyBenchmarks.cs`
   - 벤치마크 프로젝트의 Windows 대상 설정 필요 여부를 사전에 확인한다.
3. 대기 배열 축소와 비동기 대기는 별개의 변경 단위로 검토한다.
   - 수정/분리 `src/Kable.SharedMemory/Memory/SharedMemoryRingBuffer.cs`
   - 신규 후보 `src/Kable.SharedMemory/Memory/SharedMemoryRingBuffer.Waiting.cs`
   - 신규 `tests/Kable.SharedMemory.Tests/Memory/RingBufferWaitTests.cs`
   - 비동기 어댑터의 구체 파일은 신호·취소 설계 검토 후 확정한다.
4. 바이너리 소유권 API·파형 알림·UI 갱신·PCAP flush 변경은 각각 별도 제안으로 유지한다.
   - 승인 전 공용 인터페이스·기본 지연·drop·flush 정책을 변경하지 않는다.

각 구현 단위는 테스트 선작성 → 최소 구현 → 해당 대상 빌드·테스트 → 측정 → 검증된 단위 커밋 순서다.
기존 작업 트리 변경을 초기화하는 git reset은 실행하지 않는다.
