# UI 재접속·안전성 보완 및 성능 검증 결과

검증일: 2026-10-27. [승인 계획](SHARED_MEMORY_RECONNECTION_PLAN.md)과 [사용법](SHARED_MEMORY_RECONNECTION.md)을 따른다.

## 1. 구현 결과

- 장비 연결을 소유하지 않는 영속 SharedMemoryServerListener와 UI SharedMemoryClientFactory를 추가했다.
- UI 정상 종료/강제 종료는 제어용 비동기 NamedPipe 단절로 감지한다. 별도 Process 객체는 요구하지 않는다.
- 재접속 때마다 GUID별 새 MMF를 사용한다. 이전 세대의 버퍼를 초기화해서 재사용하지 않는다.
- 사용 중인 UI를 다른 UI가 강제로 교체하지 않는다. 중복 리스너도 거절한다.
- 물리 MMF는 CreateNew로 생성해 중복 이름 덮어쓰기를 막았다.
- 헤더 버전/용량/마스크/뷰 크기/닫힘을 검사하고 실패 경로의 자원 소유권과 반환을 명확히 했다.
- endpoint 준비 실패 시 기존 서버의 공유 닫힘 상태를 바꾸지 않고 로컬 자원만 반환한다.
- IConnectionContext/IProtocolCodec/IDeviceSession 선언, SPSC, 장비 FIFO 수명 계약은 유지한다.

기존 저수준 API에 자동 복구를 덧붙인 것이 아니다. 새 관리형 API를 사용하는 연결에 적용된다.
기존 호스트 앱에는 공유 메모리 연결 사용처가 없어 그 장비 로직을 수정하지 않았다.
대신 이미 시작된 장비 세션을 인자로 받는 컴파일 가능한 호스트/UI 사용 예제를 제공했다.

관련 소스·테스트·샘플 파일은 각각 300줄 미만으로 유지했다.

### 실제 독립 UI 프로세스 종료·재실행

UiRestartProcessTests는 다음 순서를 수행한다.

1. 장비 역할의 별도 InMemory 연결에 실제 KableSession을 한 번 시작한다.
2. 독립 dotnet UI 프로세스가 관리형 IPC로 접속해 EXEC 요청을 보낸다.
3. 서버가 장비로 EXEC를 전달하고 장비 응답을 보류한다.
4. UI 프로세스를 Kill한다. UI의 IPC만 닫히고 장비 세션과 진행 명령은 유지된다.
5. 이전 MMF 참조를 의도적으로 보유한 채 새 UI 프로세스를 실행해 같은 논리 채널로 접속한다.
6. 새 세대가 생성되고 장비 명령을 완료한다. 장비 연결 횟수 1, EXEC 실행 횟수 1을 확인한다.
7. 이전 IPC의 늦은 응답이 새 UI의 snapshot 응답에 섞이지 않는지 확인한다.
8. 같은 장비 세션으로 STATUS 요청이 성공하는지 확인한다.

장비는 합성 연결이며 실제 PLC/계측기를 시험한 것은 아니다.
특정 장비의 상태 snapshot·권한·업무 명령 중재는 상위 앱의 책임으로 남는다.

### 오류·수명·자원

- 잘못된 버전/용량/마스크/상태, 닫힌 매핑, 중복 생성 및 다른 크기 생성 거절.
- 누락 이벤트, 두 번째 링 실패, 기존 이벤트 충돌 후 복구와 기존 데이터 보존.
- 활성 UI 중복 접속, 중복 리스너, accept/connect 취소와 timeout, 16개 대기 accept 동시 종료.
- 잘못된 요청/서버 응답/ACK, ACK 전 단절·무응답 후 다음 정상 접속.
- 기존 데이터 무유실·포화·경합·종료 및 실제 프로세스 IPC 테스트 유지.
- 반복 접속에서 종료 직후 네이티브 핸들이 늘어나는 관측이 있었다.
  100ms callback 정리 대기만으로는 전체 테스트 실행 환경에서 항상 기준선으로 돌아오지 않았다.
  GC/finalizer를 포함해 기준선을 안정화한 뒤 100회 재접속의 증가가 16개 미만인지 검증했다.
  따라서 “Dispose 반환 직후 모든 런타임 핸들이 즉시 사라진다”는 결론은 내리지 않는다.
- 별도로 RingBufferResources의 획득 자원은 GC 없이 SafeHandle들이 닫히는지 확인했다.
  런타임 지연 자원과 명시적 소유 자원 반환을 구분하며 모든 종류의 누수를 형식적으로 증명한 것은 아니다.

## 3. 성능 측정 방법

전체 KableSession 요청→MMF 전달→서버 에코→MMF 응답→세션 매칭 경로를 비교했다.
두 엔드포인트는 같은 프로세스 안에 있고 데이터 전송은 실제 MMF를 사용한다.
실장비 응답 시간·네트워크·독립 프로세스 스케줄링을 포함하는 성능 수치는 아니다.

비교 대상:

- baseline: 최적화 전 `75cb0f8`의 Kable.SharedMemory 소스만 artifacts에 내보내 빌드.
- raw: 현재 저수준 전송. 직접 복사·비동기 대기·안전성 보완 포함.
- managed: 현재 전송에 제어 파이프와 재접속 세대 수명 감시 포함.

세 대상은 같은 현재 Kable/Core 바이너리를 사용했다. SHA-256이 모두 동일함을 확인했다.
사용자 작업 트리를 reset하거나 과거 전체 저장소로 되돌리지 않았다.
비교에는 현재 작업 트리의 다른 기존 변경이 포함된 엔진/Core를 공통으로 사용했다.

환경: Windows 11, Intel Core 7 150U, .NET SDK 10.0.301, Runtime 10.0.9, Release.
요청/응답은 ASCII 문자열 API, 관측기 없음, 연결별 워밍업 100회.
동기 기준선의 스레드 고갈로 드라이버 자체가 멈추지 않도록 세 대상 모두 같은 최소 ThreadPool 설정
max(기존 최소값, 연결 쌍 수×4+16)을 사용했다. 기본 ThreadPool 확장 속도 비교는 아니다.

32/1024자 × 연결 1/32쌍 × 세 대상 × 독립 프로세스 3회로 요청 비교 36개를 수행했다.
단일 연결은 실행당 20000회, 32쌍은 쌍당 2000회 요청이다. 실행 순서는 회차별로 반전했다.
버스트/스트림을 각각 세 대상으로 추가해 단기 측정은 총 42개다.
별도로 baseline/managed에서 1024자 단일 연결을 60초씩 수행했다.

p50/p95/p99는 1µs 구간 히스토그램으로 집계했다. 100ms 초과는 별도 건수/최댓값으로 확인하며
이번 요청 측정의 초과 건수는 0이었다. 스트림에는 메시지별 시간표시가 없어 p99를 계산하지 않았다.
GC 할당/중단시간은 에코·프로파일러를 포함한 전체 프로세스 비용이다.

## 4. 단기 요청 비교

각 p99는 3회 실행 값의 중앙값이다. 괄호는 최소~최대이며 통계적 신뢰구간이 아니다.
평균은 세 실행의 작업당 평균을 다시 평균한 값이다.

| 연결 쌍 / 문자 수 | baseline p99 | raw p99 | managed p99 | baseline / managed 평균 |
| --- | --- | --- | --- | --- |
| 1 / 32 | 118µs (98~125) | 99µs (76~152) | 92µs (91~139) | 42.2 / 48.9µs |
| 1 / 1024 | 90µs (62~98) | 128µs (85~159) | 133µs (83~146) | 41.5 / 50.6µs |
| 32 / 32 | 2666µs (2485~2710) | 1551µs (1450~1646) | 1584µs (1547~1687) | 184.9 / 512.4µs |
| 32 / 1024 | 5589µs (5367~5622) | 1639µs (1569~1680) | 1687µs (1653~1826) | 244.8 / 577.2µs |

다중 연결에서 p99는 줄었지만 평균은 늘었다. 꼬리 지연 감소를 평균/처리량 개선과 동일시하지 않는다.
raw와 managed가 비슷해 재접속용 제어 감시가 데이터 경로를 크게 바꾸는 관측은 없었다.
그러나 3회 단기 측정만으로 “오버헤드가 없다”는 보장은 하지 않는다.

버스트는 32개 요청마다 Task.Delay(1)를 넣는 단기 workload로, timer 해상도 영향을 받는다.
p99는 baseline 327µs, raw 353µs, managed 392µs였다(각 1회 측정).
스트림은 32자 메시지 100000개 무유실 수신에서 각각 약 92.2만/131.7만/147.9만 메시지/초였다.
스트림은 매우 짧은 단회 측정이므로 지속 처리량 보장이나 확정 개선율로 사용하지 않는다.

| 지표 | baseline | managed |
| --- | --- | --- |
| 처리 요청 | 2582392 | 2348815 |
| 초당 요청 | 43040 | 39147 |
| 평균 / p99 | 23.16 / 40µs | 25.46 / 50µs |
| 할당/요청 | 6847.5B | 7792.0B |

제어 응답 지연 우선 기준에서는 평균 약 10% 증가, p99 40→50µs는 회귀 관측이다.
CPU 절약이나 다중 연결 p99 감소로 이 회귀를 숨기지 않는다.
원인은 이 비교만으로 단일 함수에 귀속시키지 않지만, 등록/재개·추가 할당 경로를 후속 조사 대상으로 둔다.
현재 변경을 모든 제어 시나리오의 속도 개선으로 채택했다고 주장하지 않는다.
60초는 초기 지속 부하 선별이며, 교대 운전·실장비 장기 안정성 검증을 대체하지 않는다.

## 6. 적용 판단과 남은 범위

기능 측면: UI 중단/재실행과 장비 수명 분리, 기존 세대 데이터 격리는 구현·검증했다.
성능 측면: 다중 연결 꼬리 지연/일부 처리량과 단일 요청 평균·할당 사이에 교환이 있다.
단일 연결의 응답 지연이 중요한 제품은 허용 p99 확인과 대기 경로의 추가 개선/비교가 필요하다.
이 결과만으로 객체 풀링·임의 배치 대기·장비 요청 자동 재전송을 도입하지 않았다.

지원 제한:

- 관리형 연결은 같은 Windows 사용자 사이의 로컬 IPC다.
- 정상 연결 중 두 번째 UI가 기존 UI를 추방하는 기능은 없다.
- 살아 있는 프로세스의 hang, 실제 장비 상태 동기화 프로토콜, 사업별 권한/명령 중재는 앱 책임이다.
- 전송 종료는 장비 명령 결과나 상대 앱의 디스크 기록 완료를 보장하지 않는다.
- 기존 저수준 API 호출 코드를 새 리스너/팩토리로 바꾸는 앱 통합은 호출 앱에서 수행해야 한다.
