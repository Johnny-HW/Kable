# 장비 통신 오류 처리 비교

## 공정성 기준

라이브러리의 내부 정책을 합격 기준으로 사용하지 않는다.
취소된 요청의 늦은 응답을 다음 요청의 정상 응답으로 반환하지 않는 것,
상대방의 명시적 연결 종료·사용자 취소 후 대기 작업을 종료하는 것을 공통 요구사항으로 한다.
연결을 닫거나 다음 요청을 거절해 정확성을 지킨 결과와 정상 응답을 받은 결과는 구분한다.
종합 점수나 라이브러리 순위는 산출하지 않는다.

이 결과는 **현재 저장소의 비교 어댑터와 사용 패턴**에 대한 관측이다.
.NET·TouchSocket·SuperSocket·DotNetty의 모든 기본 기능이나 최선의 구현을 평가한 결과가 아니다.
Kable에는 장비 요청–응답 정책이 내장되어 있고, 나머지 어댑터는 간단한 응답 대기 구현이다.
따라서 raw 결과만으로 라이브러리 자체의 오류 처리 우열을 주장할 수 없다.

| 모드 | 구성 | 해석 |
| --- | --- | --- |
| raw | 기존 비교용 API·어댑터. 모든 어댑터에 송신 전 취소 검사 적용 | 해당 예제 구현에 추가로 필요한 정책 확인 |
| guarded | 모든 구현에 같은 GuardedClient 적용. Kable도 동일 적용 | 같은 애플리케이션 정책으로 요구사항을 만족할 수 있는지 확인 |

GuardedClient는 요청을 SemaphoreSlim으로 직렬화하고, 실행 중 요청이 실패하면
그 클라이언트를 사용 불가로 표시한다. 이후 요청은 거절하며 자동 재연결·명령 재전송을 하지 않는다.
토큰이 이미 취소되었거나 게이트 대기 중 취소된 호출은 송신하지 않는다.
내부 클라이언트는 각 시나리오 종료 시 DisposeAsync로 해제한다.
클라이언트가 응답하지 않으면 원래 연결에서 명령을 안전하게 다시 실행할 수 있다는 보장은 하지 않는다.

## 시나리오와 합격 기준

| 시나리오 | 주입 방법 | 기록 및 기준 |
| --- | --- | --- |
| pre-cancel | 호출 전 토큰 취소, 정상 에코 서버 연결 | 취소 예외, 20ms 관찰 창에서 수신 명령 0개 |
| cancel-inflight | 서버가 A를 수신한 뒤 토큰 취소 | 취소 예외, 취소 호출부터 반환까지 지연 |
| deadline | 응답 없는 서버에 호출자 토큰 CancelAfter(100ms) | 취소 예외, 전체 소요 시간과 100ms 대비 초과 시간 |
| disconnect | 서버가 A를 받은 후 신호에 따라 연결 종료 | 취소가 아닌 실패로 대기 종료, 종료 신호부터 반환까지 지연 |
| late-reply | A 수신 확인 → A 취소 완료 → B 시작 → A의 응답 전송 | B에 A를 반환하면 WrongReply; B 거절은 SafeRejected; B 반환은 CorrectReply |
| queued-disconnect | A 응답 대기 중 15개 요청 추가 후 상대방 연결 종료 | guarded만 측정. 총 16개가 성공·영구 대기 없이 모두 실패 종료 |

raw 모드의 queued-disconnect는 다섯 구현 모두 NotTested로 기록한다.
원래 어댑터 인터페이스가 동일 연결의 동시 호출 계약을 정의하지 않았기 때문이다.
Kable이 해당 기능을 제공하더라도 이 모드에서는 별도로 가산점을 주지 않는다.

- 원격 종료는 TCP FIN이다. 케이블 제거·무응답 네트워크·OS keepalive 감지 시간과 다르다.
- deadline은 **호출자 취소 토큰의 제한 시간**이며 각 라이브러리의 네이티브 타임아웃을 비교하지 않는다.
  Kable 어댑터의 내장 10초 타임아웃보다 먼저 100ms 취소가 발생한다.
- 자동 재연결·명령 재전송은 사용하지 않는다. 해당 기능의 정확성을 검증한 결과도 아니다.
- 각 시나리오는 매번 새 TCP 연결을 사용한다. raw의 late-reply는 A와 B에 같은 연결을 사용한다.
- 네트워크는 IPv4 루프백, ASCII+LF, 양쪽 TCP NoDelay=true다.
- 연결은 지연 측정 밖에 있다. 취소·실패 경로의 첫 실행 JIT 비용은 일부 샘플에 포함될 수 있다.
- 작업 관찰 watchdog은 2초, 수신 확인 제한 3초, 연결 제한 5초다.
  실패를 빠른 성공으로 합산하지 않고 Watchdog/HarnessFailure/CleanupFailure로 구분한다.
- 종료 지연은 CleanupMs로 따로 기록한다. 비동기 작업의 제한은 동기 라이브러리 코드 실행을
  강제 중단하지 못하므로 프로세스 전체에도 10분 제한을 둔다.
- 사전 취소의 20ms 관찰은 이 통제된 로컬 실행에서의 결과이며 모든 스케줄링에 대한 증명은 아니다.
- 늦은 응답 재현에 시간 차이를 추측하지 않고 서버 수신·해제 신호를 사용한다.

## 자원 관측

라이브러리·모드마다 별도 프로세스에서 수행한다. 실행 순서는 고정 시드로 섞는다.
오류 시나리오 이후 10회 연결·수신 확인·취소·해제를 워밍업하고, 추가 100회를 실행한다.
워밍업 후와 25/50/75/100회 지점의 관리 힙·프로세스 private bytes·핸들·스레드를 기록한다.
각 체크포인트는 100ms 정착 후 강제 GC를 수행한다. 강제 GC는 반응 시간 측정 중에는 사용하지 않는다.

DotNetty는 TCP 연결이 없는 런타임 임대 객체 하나를 워커 수명 동안 유지하여 이벤트 루프를 재사용한다.
연결마다 이벤트 루프까지 재생성해서 생기는 버퍼 풀 확장을 연결 누수로 오해하지 않기 위함이다.
다른 라이브러리도 각자의 기본 공유 실행기를 사용한다. 연결마다 클라이언트 객체는 새로 만든다.

메모리는 서버·측정기·라이브러리를 포함한 프로세스 수치다. OS 핸들은 소켓만의 개수가 아니다.
스레드 풀·메모리 풀·JIT 캐시 확장 때문에 증가량이 곧 누수는 아니다.
100회 관측만으로 장시간 누수가 없다고 결론 내리지 않는다. TCP 시스템 전체 연결 수는
프로세스별 분리가 어려워 지표에 포함하지 않았다.

## 구현의 영향을 구분한 부분

예비 실행에서 비교 어댑터의 취소 사전 검사 누락과, DotNetty 실행기 재생성에 따른
메모리 풀 확장을 확인했다. 최종 실행 전에 공통 사전 검사와 실행기 재사용을 적용했다.
TouchSocket 종료는 CloseAsync 후 Dispose를 호출한다. 예비 실행 결과는 최종 표에 섞지 않는다.
이 변경은 프로덕션 Kable API나 외부 라이브러리 소스를 수정하지 않는다.

TouchSocket의 WaitingClient, 각 라이브러리별 재연결 플러그인과 CID 구현은 사용하지 않았다.
raw의 응답 오염은 해당 어댑터에 안전 정책이 부족하다는 증거이며 라이브러리가
안전하게 구현될 수 없다는 증거가 아니다. guarded 결과가 이 구분을 확인한다.

## 실행

```powershell
dotnet test tests/Kable.Tests/Kable.Tests.csproj -c Release
dotnet run --project tests/Kable.Comparison.Benchmarks -c Release --no-build -- --faults --trials 20 --cycles 100 --output artifacts/fault-comparison
```

빌드·테스트·다른 벤치마크와 병행하지 않는다. 결과는 fault-results.md,
라이브러리·모드별 trials-*.csv, resources.csv, environment.json, 워커별 원시 JSON이다.
시나리오당 20회는 초기 비교다. p95는 19번째 값, p99는 최대값이며 신뢰구간이 아니다.
환경·콜드 경로·스케줄러 영향을 고려해야 하므로 작은 지연 차이에 순위를 매기지 않는다.
CSV에 개별 예외 형식·응답 내용·송신 관측 수·종료 시간을 보존한다.
late-reply의 LatencyMs는 A의 취소 반환 시간이다. B의 응답 오염 여부는 Outcome/Detail로 판단한다.
CleanupMs는 클라이언트 해제 시간이며 모의 서버 자체의 종료 시간은 포함하지 않는다.

### 동일 보호 정책 적용 결과

600개 관측 모두 기준을 만족했다. 취소된 클라이언트 재사용은 다섯 구현 모두 거절했다.
즉, 늦은 응답 오염 0/100회는 **같은 연결에서 다음 요청을 계속 성공시켰다는 뜻이 아니다.**
연결 종료 시 16개 대기를 모두 종료하는 100개 관측에서, 미완료 대기와 잘못된 성공은 0개였다.
사전 취소 시 명령 송신도 0/100회였다.

| 구현 | 취소 반환 p95 | 상대방 종료 후 실패 반환 p95 | 16개 대기 종료 p95 |
| --- | ---: | ---: | ---: |
| .NET 기본 API + 공통 정책 | 0.117ms | 0.324ms | 0.531ms |
| Kable + 공통 정책 | 0.328ms | 0.097ms | 0.327ms |
| TouchSocket + 공통 정책 | 0.162ms | 0.129ms | 0.315ms |
| SuperSocket + 공통 정책 | 0.116ms | 0.189ms | 0.371ms |
| DotNetty + 공통 정책 | 0.548ms | 0.555ms | 0.285ms |

100ms 호출자 제한의 실제 반환 시간은 p95 약 108~114ms였다.
Kable은 p95 109.805ms, 최대 111.472ms로 이 환경에서 설정 시간보다 늦게 반환했다.
엄격한 실시간 마감 보장으로 해석할 수 없다.
이 작은 표본과 서로 다른 콜드 경로 비용으로 라이브러리 순위를 정하지 않는다.

### 기존 어댑터 결과와 필요한 정책

| 구현 | A 취소 후 B의 결과, 20회 | 해석 |
| --- | --- | --- |
| Kable | 20회 모두 B 거절 | 내장 FIFO 수명 정책으로 오염 방지, 기존 연결 재사용 불가 |
| .NET 기본 API 예제 | 20회 모두 A를 B 응답으로 반환 | 예제에 취소 후 사용 중단·응답 식별 정책 필요 |
| TouchSocket 예제 | 20회 모두 A를 B 응답으로 반환 | 예제 응답 큐에 보호 정책 필요; WaitingClient 전체 평가 아님 |
| SuperSocket 예제 | 20회 모두 A를 B 응답으로 반환 | 예제 응답 큐에 보호 정책 필요 |
| DotNetty 예제 | 20회 모두 A를 B 응답으로 반환 | 예제 응답 큐에 보호 정책 필요 |

공통 정책을 적용하면 네 예제의 오염은 재현되지 않았다. 따라서 raw의 80개 WrongReply는
현재 예제의 부족한 계약을 보여주며 네 외부 라이브러리 자체의 결함 판정이 아니다.
모든 구현의 사전 취소·진행 중 취소·호출자 제한·상대방 종료에서는 watchdog 초과나
예상하지 않은 정상 응답이 없었다. 위 지연 수치가 기능적 성공과 별개로 반응 속도를 나타낸다.

### 종료 비용과 자원

TouchSocket의 현재 CloseAsync → Dispose 사용 경로에서는 응답 대기 취소 후
클라이언트 정리에 약 1초, 관측 최대 약 1.016초가 걸렸다.
취소 호출 반환 자체는 빨랐다. 이 종료 경로는 추가 원인 조사 대상이며
라이브러리의 모든 종료 설정이 동일하다는 뜻은 아니다.

공통 정책 모드의 100회 반복 후 관리 힙 변화는 -7,648~+13,888바이트,
핸들 변화는 -6~+1개, 스레드 변화는 0~+1개였다.
Kable은 관리 힙 +13,888바이트, 핸들·스레드는 각각 0개 변화였다.
raw Kable은 관리 힙 +23,680바이트, 핸들 +1개, 스레드 0개 변화였다.
100회 관측에서 자원이 연결 수에 비례해 크게 누적되는 현상은 보이지 않았지만
작은 증가의 원인이나 장시간 누수 유무를 확정하지 않는다.

DotNetty는 실행기와 풀을 재사용한 워밍업 후 관리 힙 기준값이 약 66.2MiB였고,
공통 정책 100회 후 증가는 약 8.8KiB였다. 다른 구현의 기준값은 약 0.3~0.5MiB였다.
이는 현재 버퍼 풀·실행기 설정의 고정 비용을 포함하므로 증가량만으로 메모리 비용을 비교해서도 안 된다.

### 후속 검토 우선순위

1. TouchSocket 현재 종료 경로의 약 1초 지연 원인 확인.
