# 공유 메모리 잔여 항목의 운영 적합성 평가

평가일: 2026-10-27. 대상: [검증 결과](SHARED_MEMORY_OPTIMIZATION_RESULTS.md)의 7절 잔여 항목.
이번 작업은 코드·기존 테스트 검토와 독립 진단 프로세스의 관측, 문서 작성이다.
프로덕션 코드와 회귀 테스트는 변경하지 않았다. 기존 성능 수치를 새로 측정한 결과로 표시하지 않는다.

## 1. 평가 결론

남은 항목을 모두 같은 수준의 “추후 검토”로 두면 안 된다.
헤더/초기화 안전성은 먼저 보완할 항목이고, SPSC와 지연 해제는 사용 계약으로 수용할 수 있다.
속도·GC 검증은 적용 효과를 판정하는 단계이며, 객체 풀링은 그 측정 뒤에 결정한다.

우선순위는 P1: 해당 운영 시나리오에 도입하기 전 해소/입증, P2: 계약·호환성 정리 또는 조건부 개선이다.
발생 확률을 측정하지 않았으므로 위험도에 임의 확률이나 점수를 붙이지 않는다.

| 선택 항목 | 평가 | 우선순위와 다음 행동 |
| --- | --- | --- |
| 실장비·장시간·p99·GC 미측정 | 성능 채택 근거가 부족 | P1: 실제 통신 경로의 변경 전/후 비교와 지속 부하 검증 |
| 상대 프로세스 강제 종료 감지 없음 | 별도 감시 없는 독립 프로세스 운영에는 부족 | P1: 프로세스 종료/응답 정지 감시의 소유 계층과 시간 계약 결정 |
| SPSC 유지 | 서버 1개·클라이언트 1개 전용 채널에서는 타당 | P2: 유지. 동일 채널 다중 연결을 지원한다고 해석하지 않도록 명시 |
| 준비 상태 재확인·중복 대기 오류 | 정합성 개선이지만 기존 호출 의미 일부 변경 | P2: 기존 소비자 호환성 검토와 릴리스 설명 필요 |
| Dispose 지연 해제 | 메모리 접근 안전성을 위한 타당한 선택 | P2: 유지. 자원 해제 완료·데이터 전달 완료와 구분 |
| 비동기 대기 객체 풀링 미적용 | 지금 바로 풀링할 근거는 부족 | P2: 실제 등록 빈도·할당·GC·p99 측정 후 결정 |
| 생성 실패·손상 헤더 자원 감사 미완료 | 단순 문서 보완으로 끝낼 수 없음 | P1: 헤더 검증·중복 생성·실패 시 소유권 정리부터 보완 |

현 상태를 “임의의 다른 프로세스와 연결해도 안전한 완성형 IPC”로 평가하지 않는다.
통제된 1:1 채널의 정상 전송·협력적 종료는 기존 검증 근거가 있지만,
공개 범용 사용에는 아래 P1 항목에 대한 설계와 추가 시험이 필요하다.

## 2. 이번에 추가 확인한 사실

Windows/.NET 10의 별도 진단 프로세스에서 임의 GUID의 자체 시험 채널만 사용했다.
손상된 헤더는 Open 결과까지만 확인하고 Read/Write를 호출하지 않았다.

| 관측 | 결과 | 의미 |
| --- | --- | --- |
| Magic은 정상, Version=999 | Open 성공 | 지원하지 않는 버전을 거절하지 않음 |
| Magic은 정상, Capacity=0, Mask=0 | Open 성공 | 생성 인자 검증과 달리 외부 헤더 용량은 검증하지 않음 |
| Capacity=256, Mask=4095 | Open 성공 | 용량과 마스크의 일관성을 검증하지 않음 |
| 1B 기록 후 같은 이름·용량으로 Create 재호출 | 기존 Reader가 0B 읽음 | 새 생성자가 기존 Head/Tail을 초기화하여 미수신 데이터가 사라짐 |
| 연결 상대 dotnet 프로세스를 Kill | 종료 토큰 미취소, Read는 200ms 뒤 호출자 취소로 종료 | 강제 종료를 자체 연결 단절로 전달하지 않음 |
| 잘못된 Magic으로 Open 실패 후 자체 자원 Dispose·GC | 대조군/실패군 모두 해당 이름으로 재열기 불가 | 남은 이름은 관측되지 않음. 모든 뷰·포인터 참조 해제의 증명은 아님 |

관측 소스와 JSON은 `artifacts/shared-memory-evaluation/`에 보관했다(Git 제외).
재현 명령: `dotnet run --project artifacts/shared-memory-evaluation/Evaluation.csproj -c Release`.
강제 종료 시험의 상대 호스트는 기존 `tests/Kable.SharedMemory.TestPeer` Release 빌드다.
200ms 관측만으로 무한 대기를 증명하지는 않는다. 다만 현재 펌프의 무제한 대기와
상대 프로세스 감시 부재를 함께 보면 별도 취소/신호 없는 자동 종료 경로가 없다고 판단된다.

## 3. 실장비·장시간·p99·GC

현재 근거는 기능 테스트, 복사 구간 측정, 유휴 대기의 스레드 점유와 등록 비용이다.
전체 경로의 응답 지연·지속 처리량·장시간 GC 영향은 이를 대신할 수 없다.

평가: 중간 복사 제거의 구조적 이점은 있어도 전체 통신이 빨라졌다고 확정할 수 없다.
특히 빈 버퍼에 자주 도착하는 단건 메시지는 대기 등록/재개 비용이 반복될 수 있다.
고빈도 단일 연결에서 더 느려지는지와 여러 연결에서 정체가 줄어드는지를 함께 비교해야 한다.

다음 검증은 별도 구현 승인 후 아래 순서로 진행한다.

1. 동일한 장비/재현 트래픽·빌드·GC 설정의 변경 전/후 기준선을 고정한다.
2. 단일 요청·응답, 연속 스트림, 간헐 버스트, 다중 연결, 느린 소비자를 분리한다.
3. 호출→응답 및 수신→소비의 p50/p95/p99와 처리량, CPU, 실제 대기 등록 수를 기록한다.
4. 전체 프로세스 할당/초, GC 횟수·중단시간, 큐 깊이, drop·오류·timeout도 기록한다.
5. 승인된 운전 지속시간 동안 위 지표와 핸들·메모리 증가를 확인한다.
   30~60분 시험은 초기 선별안일 뿐, 교대/연속 운전 요구를 충족했다고 해석하지 않는다.

합격 기준은 장비의 허용 지연·연결 수·유실 정책으로 정한다. 지금 임의 p99 목표를 정하지 않는다.
최적화가 목표 지표를 개선하지 않거나 회귀하면 대기 구현/적용 범위를 재검토한다.

## 4. 정상 종료와 비정상 종료의 구분

근거: `SharedMemoryConnectionContext.cs:73,117`의 무제한 대기,
`SharedMemoryRingBuffer.Lifetime.cs:59`의 헤더 게시와 이벤트 알림.

정상 Close/Dispose는 공유 헤더를 닫고 이벤트를 깨운다.
상대 프로세스 Kill은 이 코드를 실행하지 않아 데이터/공간 대기가 그대로 남을 수 있다.
이 문제는 기존 50ms 동기 재확인도 헤더만 읽었다면 해결하지 못한다.
따라서 “비동기화 때문에 새로 생긴 강제 종료 감지 결함”으로 분류하지 않는다.

권고: 앱이 상대 프로세스를 생성·관리한다면 그 호스트가 프로세스 종료를 관찰하고 해당 연결을 Abort한다.
상대 프로세스가 살아 있지만 응답하지 않는 경우는 별도 heartbeat/워치독의 역할이다.
단순 수신 유휴시간만으로 정상적으로 조용한 장비를 끊지 않도록 유휴 계약을 먼저 정해야 한다.
Kable의 heartbeat는 선택 사항이므로 구성 여부·해당 프로토콜의 ping/pong 지원을 확인해야 한다.

판정: 상위 감시가 이미 있으면 그 연동을 검증한 뒤 수용 가능하다.
없다면 독립 프로세스의 비정상 종료까지 Fail-Fast로 보장하는 운영에는 보완이 필요하다.
검증 대상: 유휴/송신 포화 중 Kill, 예외 종료, 응답 정지, 정상 유휴, 감시자의 동시 Dispose.
자동 명령 재전송은 추가하지 않고 기존 단일 세션 수명·새 세션 복구 계약을 유지한다.

## 5. SPSC는 결함인가

근거: `SharedMemoryRingBuffer.IO.cs`는 Head/Tail을 단일 소유자가 게시하는 구조이며
여러 작성자의 공간 예약이나 여러 소비자의 읽기 범위 예약을 수행하지 않는다.

평가: 한 채널에 서버 1개·클라이언트 1개인 용도에는 합리적이다.
여러 구독자를 지원하려고 저수준 링을 MPMC로 바꾸는 것은 이번 최적화의 자연스러운 다음 단계가 아니다.
수신한 뒤 상위 계층에서 fan-out하거나 별도 채널을 제공하는 편이 현재 경계와 맞는다.

주의: 현재 Create/Connect 팩토리는 같은 채널에 여러 프로세스가 붙는 것을 독점적으로 차단하지 않는다.
“SPSC라고 문서에 썼다”는 사실이 잘못된 다중 접속을 자동 방지한다는 뜻은 아니다.
재접속·다중 앱 실행이 실제 가능하면 초기 연결 단계의 소유자/세대 확인을 설계해야 한다.
매 Read/Write에 전역 락을 넣는 방식은 권고하지 않는다.

## 6. 준비 상태 재확인과 중복 대기의 호환성

이벤트는 남아 있을 수 있으므로 신호만 받았다고 데이터/공간이 있다고 반환하지 않는 방향은 타당하다.
호출자는 true 후에도 Read/Write 결과를 확인해야 한다. true는 연결 닫힘도 포함한다.

같은 방향에 대기 두 개를 등록하면 AutoResetEvent 신호를 경쟁 소비한다.
단일 대기자 원칙을 명시적 오류로 만든 것은 합리적이지만 기존에 성공하던 호출이 예외가 될 수 있다.
더 정확히는 미준비 상태에서 중복 대기 슬롯을 요구할 때 거절한다.
준비된 빠른 경로와 timeout=0 확인까지 모두 거절하는 전역 호출 직렬화는 아니다.

저장소의 연결 펌프는 방향마다 하나이며 이 구조와 맞는다.
하지만 외부 NuGet 소비자의 사용 방식까지 조사한 것은 아니다.
기존 동기 API도 준비 상태·timeout·취소 우선순위에 일부 관측 가능한 차이가 있으므로
“메서드 시그니처 유지 = 동작 완전 호환”이라고 설명하면 안 된다.
권고: 릴리스 설명에 중복 대기 제한과 readiness 의미를 명시하고 주요 기존 소비자를 회귀 검증한다.

## 7. Dispose의 지연 해제

평가: 진행 중 포인터 접근이 끝나기 전에 매핑을 해제하지 않는 선택은 유지하는 것이 맞다.
강제로 즉시 해제하거나 동기 spin-wait로 되돌리면 안전성·스레드 점유 문제가 재발할 수 있다.

보장 범위는 다음처럼 구분한다.

- 링 Dispose 반환: 새 접근 금지와 닫힘 게시. 진행 작업이 있으면 실제 해제는 이후다.
- 대기 Task 완료: 그 대기가 가진 접근권 반환. 다른 접근까지 모두 끝났다는 뜻은 아니다.
- 컨텍스트 DisposeAsync 완료: 자신이 소유한 두 펌프 종료를 기다린다.
  외부 호출자가 raw 링에서 시작한 임의 작업까지 모두 기다리는 API는 아니다.
- 종료 완료: 상대방의 모든 데이터 수신/기록 완료를 보장하지 않는다.
  현재 Read는 IsClosed인 링을 읽지 않으므로 잔여 데이터의 graceful drain은 별도 계약이다.

기존 경합 테스트는 안정성 근거이지만, 장시간 반복의 자원 기준선 복귀를 확인한 자료는 없다.
추가 검증: 시작·종료 반복 후 핸들/매핑·메모리 추이, 종료 완료 시간, 외부 접근권 보유 중 종료.
전송 완료 보장이 필요하면 상위 프로토콜의 확인 응답과 종료 순서를 정의한다.

## 8. 객체 풀링은 지금 필요한가

등록/게시/재개 왕복에서 약 688.52B/회가 관측됐지만 여기에는 진단 함수의 Task 등도 포함된다.
이를 라이브러리 TCS 한 개의 정확한 크기나 메시지당 고정 할당으로 해석하지 않는다.
등록 빈도가 초당 1000/10000회라면 같은 패턴의 단순 환산은 약 0.69/6.89MB/s이다.
이는 실측 부하의 할당률이 아니라 영향 크기를 이해하기 위한 예시다.

판정: 등록 빈도와 GC/p99 영향부터 측정한다. 문제가 확인되면
연결 수명 동안 재사용하는 대기 객체/등록 설계를 검토하고, 필요한 경우에 풀링을 비교한다.
늦은 callback·취소가 다음 세대 대기를 완료하지 않도록 세대 식별과 사용 종료 규칙이 필요하다.
무조건 풀링하면 복잡성·자원 수명·예전 callback의 오염 위험이 커진다.

## 9. 생성·열기·헤더 감사는 먼저 보완할 항목

근거: `SharedMemoryRingBuffer.cs:38-60,66-104`, `SharedMemoryTransport.cs:24-25,42-43`.

### 재현한 검증 누락

Open은 Magic만 검사하고 Version, Capacity의 양수/2의 거듭제곱 여부, Mask=Capacity-1,
헤더/데이터가 실제 매핑 길이 안에 있는지를 검증하지 않는다.
그 값으로 unsafe 메모리 접근 범위를 계산하므로 손상 헤더 수용은 메모리 안전성 검토 대상이다.
이번에는 잘못된 메모리를 실제로 읽거나 크래시를 유도하지 않았다.

Create는 CreateOrOpen 후 새 생성자로 헤더를 초기화한다.
같은 이름으로 두 번 생성하면 기존 데이터가 사라지는 동작을 재현했다.
생성·열기의 구분, 초기화 완료 게시, 동일 채널 소유자와 세대 계약이 필요하다.

### 실패 시 자원 소유권

AcquirePointer 이후 이벤트 열기 또는 생성자 검증이 실패하는 경로에 명시적 역순 정리가 없다.
팩토리도 두 번째 링 생성/열기가 실패했을 때 첫 번째 링을 정리하는 경로가 없다.
이 정적 사실은 확인했지만, 이번 관측만으로 영구 누수량을 확정하지 않는다.
실패 후 이름이 사라졌다는 확인도 모든 매핑 뷰/참조가 정확히 회수됐음을 뜻하지 않는다.

권고 설계: 각 단계의 자원 소유자를 하나로 정하고, 성공 때만 최종 객체에 소유권을 이전한다.
실패 시 ReleasePointer/뷰/MMF/이벤트를 획득 역순으로 정리하고, 반쪽 endpoint도 정리한다.
잘못된 매핑은 포인터 역참조 전에 길이와 헤더를 검증해 명시적 예외로 거절한다.
정상 소유자가 실행 중인 매핑을 재초기화하지 않도록 생성 계약을 먼저 확정한다.

필요 테스트: 잘못된 버전/용량/마스크/짧은 매핑, 누락된 이벤트,
첫 링 성공·두 번째 링 실패, 초기화 중 Open, 실행 중 중복 Create, 다른 크기의 기존 매핑,
반복 실패 후 자원 증가 및 실패 뒤 새 정상 연결 성공.

## 10. 권고 실행 순서와 이번 완료 범위

1. 헤더 검증·중복 생성 방지·실패 정리를 하나의 안전성 설계로 확정한다(P1).
2. 프로세스 종료 감시가 필요한 배치 구조인지 확인하고 책임과 감지 시간 계약을 정한다(P1).
3. 전체 통신 경로의 변경 전/후 속도·p99·GC와 지속 부하를 측정한다(P1).
4. SPSC·중복 대기·종료/전달 보장 차이를 소비자 계약과 릴리스 설명에 반영한다(P2).
5. 측정에서 대기 등록 할당이 실제 병목일 때 재사용·풀링을 검토한다(P2).

완료: 선택 항목별 평가, 코드/테스트 근거 확인, 자체 채널의 제한된 진단, 우선순위 문서화.
미수행: 프로덕션 수정, 새 회귀 테스트 추가, 실장비/장시간 측정, 자원 누수 확정.
이 문서는 후속 코드 변경의 승인을 대신하지 않는다.
